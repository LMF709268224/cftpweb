## 暂缓：规则不完整或冲突

1. **Finance 能否管理学员**：正文只写查看学员、管理支付和会员，表格却允许 Manage students。需要确定以哪一个为准，以及“管理”具体包含哪些 2/3 中的动作。
2. **Partial 审计范围**：是本人执行的操作、所属部门，还是允许管理的资源？必须由服务端限制列表和详情；不能只在前端加筛选，或允许用户改 `operator_id` 越过限制。
3. **Admin 的边界**：正文“manage all aspects”不能直接理解为 Super Admin；表格明确禁止 Admin 查看员工、分配员工角色、删除账号。待确认后保持这些动作独立授权。
4. **支付权限缺列**：正文提到 Finance 管理支付，矩阵没有支付动作。需细化查看订单、金额调整、退款、发票等权限；不能放开整个支付模块作为替代。
5. **旧管理员迁移**：当前仅识别配置的 `role_admin_basic`。哪些现有账号分配 Ops／Finance／Admin／Super Admin，需要实际角色配置和账号分配名单。不得自动把旧 Admin 升为 Super Admin。
6. **Every action 的完整范围**：本次补充本页明确要求的 GET 查看行为；仍需明确其他读取、导出、登录、登录失败、鉴权前拒绝和 Casdoor 控制台操作是否都纳入，以及保留期。不能宣称已覆盖系统所有动作。

## 2026-11-25 中文说明复核

中文已明确四类岗位的总体职责，并明确指出“Admin 和 Super Admin 的具体权限边界仍需确认”。因此原先没有直接套用矩阵、没有将旧 Admin 升级为 Super Admin 的处理正确。Finance 中文仍只明确查看考生、管理付款和会员，未消除表格 Manage students 的差异；Partial 审计数据范围也未补充。

“所有操作应写入审计日志”是明确目标，现有查看行为补充和业务写操作审计只算部分覆盖。登录／鉴权拒绝／Casdoor 事件及必达保证的接入仍是缺口，不因文字明确就宣称当前已覆盖。角色与审计体系变更作为较大流程事项，见[统一确认清单](chinese-notes-review.md)，等用户确定后实施。
