# CFTP 系统架构与生产环境部署说明

本文档用于 CFTP 认证培训平台正式环境的资源准备、部署实施和上线验收。系统包含考生端、管理端、BFF、认证服务、Go 微服务及数据库、缓存、消息、对象存储和日志监控等基础设施。

> 本文档中的资源规格是生产环境建议基线，不代表容量承诺。正式规格需结合注册用户数、峰值并发、课件与视频容量、日志保留周期及备份要求最终确认。

## 1. 客户需提供的资料与资源

以下内容应在部署开始前准备完毕。账号、密码、私钥和第三方密钥不得通过普通聊天工具或明文邮件传递，应使用双方确认的安全渠道交付。

### 1.1 服务器与访问权限

| 项目 | 建议/要求 | 客户需提供 |
| --- | --- | --- |
| 应用节点 | 2 台；每台至少 8 vCPU、16 GB 内存、200 GB SSD/NVMe | 内网 IP、主机名、SSH 端口、运维账号及授权方式 |
| 操作系统 | Ubuntu Server 22.04 LTS 或 24.04 LTS，64 位 | 操作系统版本及补丁策略 |
| 集群 | K3s/Kubernetes；生产环境关键服务至少 2 副本 | 是否已有集群；如已有，提供集群访问方式、命名空间和存储类 |
| 容器镜像仓库 | 客户私有 Registry 或双方确认的镜像交付方式 | Registry 地址、项目名称、推送/拉取凭据 |
| 网络 | 节点内网互通，具备所需外网访问能力 | 防火墙策略、代理信息、出口 IP、需走审批的端口清单 |
| 运维基础 | DNS、NTP/时间同步、备份存储可用 | 堡垒机/VPN、变更窗口和运维联系人 |

如客户已有负载均衡、Kubernetes、日志平台或备份平台，应同时提供接入规范。若只能提供单个应用节点，系统可以部署，但不具备节点级高可用能力，不能作为推荐的正式环境方案。

### 1.2 域名、证书与公网入口

客户需确认并提供：

- 考生端域名，例如 `candidate.example.com`；
- 管理端域名，例如 `admin.example.com`；
- 认证中心域名，例如 `auth.example.com`；
- 支付、考试等第三方回调所需的公网域名和路径；
- DNS 解析操作权限，或负责配合添加 A/CNAME/TXT 记录的联系人；
- TLS 证书及完整证书链、私钥，或允许自动签发证书所需的 DNS/HTTP 验证条件；
- 公网负载均衡/WAF 的地址、回源规则和真实客户端 IP 转发规范（如适用）。

正式环境仅开放 HTTPS。管理端如需限制访问范围，客户应提供 VPN、办公网或 IP 白名单要求。

### 1.3 PostgreSQL

生产环境推荐使用客户已有的托管 PostgreSQL 服务，建议基线为 4～8 vCPU、16～32 GB 内存，并启用高可用和自动备份。客户需提供：

- PostgreSQL 版本（建议 14 或以上）、主机、端口及 TLS 要求；
- 数据库/Schema 的命名规范，以及建库、建表和初始化数据的执行权限；
- 应用账号和部署初始化账号，两者权限应按最小权限原则区分；
- 网络白名单或安全组配置方式；
- 高可用方案、备份周期、保留时间、恢复点目标（RPO）和恢复时间目标（RTO）；
- 监控、慢查询和磁盘容量告警的责任人。

各微服务使用独立 Database 还是独立 Schema，必须以后台微服务仓库中的实际连接配置和 SQL 脚本为准，在部署评审时确认，不在部署现场临时推断。

### 1.4 Redis

生产环境推荐使用托管 Redis，建议基线为 2～4 vCPU、8～16 GB 内存。客户需提供：

- Redis 版本（建议 6.0 或以上）、访问地址、端口、账号/密码及 TLS 要求；
- 实例模式（主从/Sentinel/Cluster/托管高可用）和持久化策略；
- 网络白名单、安全组和最大连接数限制；
- 内存淘汰策略、备份恢复策略和容量告警联系人。

不建议在生产环境中仅部署两个自建 Redis 节点实现自动仲裁；如必须自建，应采用经过评审的 Sentinel 或 Cluster 高可用方案。

### 1.5 对象存储

生产环境优先使用 S3/OSS 等托管对象存储；私有化环境可部署 MinIO。客户需提供：

- 服务 Endpoint、Region、Bucket 名称；
- Access Key、Secret Key，或等效的工作负载身份授权方式；
- 公网/内网访问方式、CORS 规则和允许的文件类型/大小限制；
- 容量、生命周期、版本控制、备份及跨区域容灾要求；
- 如使用 CDN，提供加速域名、回源和缓存刷新方式。

如由客户提供自建 MinIO，还需明确节点、磁盘、纠删码、高可用和备份方案。对象存储不能只依赖应用节点本地临时磁盘。

### 1.6 外部系统与业务账号

| 系统 | 客户需提供/确认 |
| --- | --- |
| SMTP/邮件服务 | SMTP 主机、端口、加密方式、发信账号和密码/令牌、发件人地址；发信域名的 SPF、DKIM、DMARC 配置责任人 |
| Stripe | 正式环境 Publishable Key、Secret Key、Webhook Secret、币种和商户账号；Webhook 地址上线后再按最终域名登记 |
| Prometric/GEE | 正式接口地址、账号/凭据、接口文档、网络白名单、回调规范及对方联调联系人 |
| Casdoor | 初始超级管理员信息、组织名称、考生端和管理端应用名称、允许的回调域名；Client ID/Secret 由部署配置后安全登记 |
| 企业微信告警 | 群机器人 Webhook 或 Grafana 联系点所需信息、告警接收人和升级联系人 |

不启用的外部系统也应由客户书面确认，并说明相关业务功能在首期是否关闭。

### 1.7 安全与运维要求

客户需在上线前确认：

- Secret/KMS/OpenBao 或客户现有密钥管理方案；
- 密码复杂度、账号生命周期、MFA 和管理员授权规则；
- WAF、防火墙、安全组、漏洞扫描和等保/审计要求；
- 日志保留周期、备份保留周期及数据合规要求；
- 生产发布窗口、故障通知机制、客户与实施方责任人；
- 备份恢复演练、应急预案和回滚要求。

## 2. 系统架构

### 2.1 整体拓扑

```text
用户浏览器
    |
    v
公网负载均衡 / WAF / Traefik Ingress（HTTPS）
    |
    +--> 考生端 candweb --> candbff --+
    |                                  |
    +--> 管理端 adminweb --> adminbff -+--> Go gRPC 微服务集群
    |                                  |       |
    +--> Casdoor（统一认证）            |       +--> PostgreSQL
                                       |       +--> Redis
                                       |       +--> NATS JetStream
                                       |       +--> MinIO / S3 / OSS
                                       |
                                       +--> SMTP / Stripe / Prometric / GEE

应用与基础设施日志 --> Vector --> Loki --> Grafana / 企业微信告警
```

### 2.2 组件职责

| 层级 | 组件 | 职责 |
| --- | --- | --- |
| 接入层 | Traefik/Ingress、负载均衡/WAF | HTTPS 终止、域名及路径路由、访问控制 |

| 文件存储 | MinIO/S3/OSS | 图片、视频、学习资料和 PDF 文件 |
| 可观测性 | Vector、Loki、Grafana | 日志采集、检索、看板和告警 |

## 3. 推荐生产部署方案

### 3.1 应用与数据分离

推荐采用“2 台应用节点 + 托管 PostgreSQL/Redis + 托管对象存储”的方案：

- 两台应用节点组成 K3s/Kubernetes 集群，关键无状态服务部署 2 副本并分散到不同节点；
- PostgreSQL 和 Redis 使用客户托管服务，避免在两台应用节点上同时承担数据高可用；
- 对象文件使用 S3/OSS，或使用具备独立磁盘与备份方案的高可用 MinIO；
- NATS JetStream 启用持久化存储。其副本数、磁盘和故障域应根据可用节点数评审，不能仅通过增加 Pod 副本宣称高可用；
- Traefik/Ingress 负责集群入口；如客户已有公网负载均衡或 WAF，应部署在 Ingress 前方；
- 生产工作负载配置资源 requests/limits、健康检查、反亲和性或拓扑分布约束及 PodDisruptionBudget。

两节点架构可承受单个应用节点故障，但集群控制面仲裁、持久化中间件和计划维护仍可能受限。若客户要求严格的自动故障切换和控制面高可用，建议提供至少 3 个满足故障域要求的节点，或采用托管 Kubernetes。

### 3.2 规格建议

| 资源 | 建议基线 | 说明 |
| --- | --- | --- |
| 应用节点 | 2 × 8 vCPU、16～32 GB、200 GB SSD/NVMe | 承载 Ingress、Casdoor、BFF、业务服务和日志采集 |
| PostgreSQL | 4～8 vCPU、16～32 GB、500 GB 起 | 托管高可用；容量按业务数据与备份增长评估 |
| Redis | 2～4 vCPU、8～16 GB | 托管高可用；按峰值连接和热数据量评估 |
| 对象存储 | 1 TB 起或按量托管 | 按视频/课件规模、版本和保留期评估 |
| 日志存储 | 独立 200 GB 起或托管日志平台 | 按每日增量和保留周期计算，避免占满应用盘 |
| 网络 | 节点至少 1 Gbps | 上传下载量大时需单独评估公网带宽和 CDN |

若将 PostgreSQL、Redis、MinIO 和 Loki 全部自建，必须增加独立数据节点并单独设计备份、仲裁、监控和故障恢复，不应与上述两台应用节点基线混用。

## 4. 部署实施

### 4.1 部署物与环境配置

本仓库的 `deployment/` 目录只包含 `adminweb`、`adminbff`、`candweb`、`candbff` 和 Web Ingress 的 Kubernetes 清单。`cfgserver`、业务微服务、Casdoor、NATS、MinIO 及监控组件的部署物，应从对应后台仓库或经双方确认的发布包获取。

现有仓库清单包含测试命名空间、测试域名、测试镜像名和单副本配置，不能原样用于生产。生产发布前必须完成环境参数化，并将凭据迁移到 Kubernetes Secret 或客户指定的密钥管理系统。严禁把正式密码、私钥或 API Secret 写入 Git 中。

建议建立生产参数表，至少包含：

- Kubernetes namespace、镜像版本与镜像拉取 Secret；
- 全部域名、Ingress、TLS Secret 和回调 URL；
- `cfgserver` 地址及各服务间 TLS 证书；
- PostgreSQL、Redis、NATS 和对象存储连接参数；
- Casdoor、SMTP、Stripe、Prometric/GEE 配置；
- 副本数、资源 requests/limits、存储类和 PVC 大小；
- 日志级别、日志保留期和告警联系点。

### 4.2 数据库初始化

在业务微服务启动前，须使用与正式发布版本匹配的后台仓库 SQL 脚本完成建库、建表和种子数据初始化。实施前应形成可审核的脚本清单，记录服务名、目标 Database/Schema、脚本路径、版本、校验值、执行顺序和执行结果。

基本原则如下：

1. 先备份，并在测试环境验证同版本脚本；
2. 按后台仓库说明创建 Database/Schema 和最小权限账号；
3. 先执行表结构/迁移脚本，再执行明确标注为生产可用的初始化数据脚本；
4. 不根据文件名猜测脚本作用，不把演示或测试数据导入生产；
5. 初始化完成后核对表、约束、索引、版本表和关键种子数据；
6. 保存执行日志，并在应用上线前完成一次可恢复性确认。

具体 SQL 文件名和顺序以最终交付的后台服务版本为准。当前 Web 仓库不包含这些 SQL 脚本，因此不能仅依据本文档中的示例命令执行生产初始化。

### 4.3 Casdoor 初始化

1. 部署 Casdoor 并连接正式数据库；
2. 创建 CFTP 组织和初始超级管理员；
3. 分别创建管理端、考生端应用，登记准确的回调 URL；
4. 配置 Provider、角色和权限策略；
5. 将 Client ID、Client Secret 等配置通过 Secret/配置中心交付给对应服务；
6. 分别验证管理端、考生端登录、退出、令牌刷新和无权限访问场景。

### 4.4 推荐部署顺序

1. 完成服务器、网络、DNS、Registry、存储类和密钥管理准备；
2. 验证 PostgreSQL、Redis、对象存储等托管资源的连通性、备份和监控；
3. 部署 NATS JetStream，并验证持久化；
4. 执行经审核的数据结构与生产种子数据初始化；
5. 部署并初始化 Casdoor；
6. 部署 `cfgserver`，逐项核对生产配置；
7. 按后台仓库定义的依赖顺序部署 `gmid`、`gcc` 及其他业务微服务；
8. 部署 `adminbff`、`candbff`，再部署 `adminweb`、`candweb`；
9. 配置 Ingress、正式域名和 TLS；
10. 接通 SMTP、Stripe、Prometric/GEE，并完成回调验证；
11. 部署或接入 Vector、Loki、Grafana，配置告警；
12. 执行上线验收、备份恢复验证和回滚演练。

## 5. 上线验收

### 5.1 基础设施验收

- 所有节点状态正常，时间同步正确，磁盘、CPU 和内存无异常；
- 关键工作负载分布在不同节点，健康检查、资源限制和重启策略生效；
- PostgreSQL、Redis、NATS、对象存储的连接、持久化、备份和告警有效；
- 域名解析正确，TLS 证书链完整且自动续期/更换责任明确；
- 网络策略、安全组、WAF 和管理端访问限制符合要求；
- Git、镜像和 Kubernetes 配置中不存在明文正式密钥。

### 5.2 功能验收

- 管理端和考生端均可访问，Casdoor 登录、退出和权限校验正常；
- 课程/认证目录、学习资料、进度推进等核心流程正常；
- 商品下单、Stripe 支付及 Webhook 回调形成闭环；
- 考试预约、代码获取、成绩回传可以联调完成；
- 邮件、站内信、证书/PDF 生成和对象上传下载正常；
- 审计日志、应用日志、Grafana 查询和企业微信告警正常。

### 5.3 运维验收与交付物

- 镜像版本、配置版本、数据库脚本版本和部署记录；
- 生产拓扑、域名、端口和外部依赖清单；
- Secret 保管及轮换责任说明（交付物中不记录明文值）；
- 备份策略、恢复步骤及最近一次恢复验证记录；
- 监控看板、告警规则、值班和升级联系人；
- 发布、回滚、扩容、证书更新和常见故障处理手册；
- 双方签字或确认的上线验收记录及未决事项清单。

## 6. 主要风险与边界

- “1 万级用户”不能直接换算为机器规格，必须提供峰值并发、请求量、文件容量和增长率后再做容量评估与压测；
- 两台应用节点不等于所有组件都自动高可用，数据库、缓存、消息、对象存储和 Kubernetes 控制面需分别评审；
- 日志和对象文件增长通常快于业务数据库，应设置容量告警、生命周期和独立备份；
- 第三方正式凭据未交付或网络白名单未开通时，只能完成内部部署，不能视为支付、邮件或考试链路已上线；
- 数据库结构、初始化脚本和配置字段必须以本次发布版本的服务契约为准，不得通过复制或猜测配置值绕过启动错误。
