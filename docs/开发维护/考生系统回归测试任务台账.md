# 考生系统回归测试任务台账

## 1. 文档用途

本文档是考生系统回归测试任务的统一台账，用于记录：

- 当前有哪些 GitHub Actions 测试任务。
- 每个任务由什么事件驱动。
- 每个任务测试什么、不测试什么。
- 测试使用 Mock 数据还是真实测试环境。
- 新增、修改、删除任务时需要同步维护哪些文件。
- 测试账号、Token、报告和真实数据的安全边界。

GitHub Actions 的实际执行配置以
`.github/workflows/candidate-e2e.yml` 为准。本文档用于解释和维护该配置，
修改工作流时必须同步更新本文档。

当前基线日期：`2026-08-06`。

## 2. 三个任务总览

| 编号 | GitHub Actions Job | 主要测试对象 | 数据来源 | 是否访问真实环境 | 是否允许修改业务数据 |
| --- | --- | --- | --- | --- | --- |
| 任务一 | `Candidate BFF regression` | Go BFF、HTTP 路由、Handler 业务逻辑 | Fake gRPC Client | 否 | 否 |
| 任务二 | `Candidate Playwright regression` | Vue 页面、浏览器交互、Token 和订单体验 | 浏览器 API Mock | 否 | 否 |
| 任务三 | `Candidate live regression` | 真实 Casdoor、真实站点、真实 BFF、微服务和 Stripe Test Mode；包含只读、可恢复写入和完整业务旅程阶段 | 测试环境真实数据 | 是 | 默认不修改；手动开启后允许可恢复写入或明确需要 Admin 清理的专用测试数据 |

三个任务是三层不同的保护，不互相替代：

- 任务一回答“后端接口代码和业务规则有没有被改坏”。
- 任务二回答“前端页面和用户操作流程有没有被改坏”。
- 任务三回答“部署后的真实测试环境是否连得通、登得进、读得出；手动开启
  可写阶段后，真实写接口是否可执行并能恢复或清理；手动开启完整旅程后，
  认证购买、Stripe 测试支付、课程学习、全部测验和正式考试报名是否真正跑通”。

## 3. 驱动方式

统一工作流名称：`Candidate Portal Regression`。

| 驱动事件 | 任务一 | 任务二 | 任务三 |
| --- | --- | --- | --- |
| Push 到 `v2` | 自动执行 | 自动执行 | 跳过 |
| Push 到 `main` | 自动执行 | 自动执行 | 跳过 |
| Pull Request 指向 `v2` | 自动执行 | 自动执行 | 跳过 |
| Pull Request 指向 `main` | 自动执行 | 自动执行 | 跳过 |
| Actions 手动运行，`run_live_readonly=true` | 执行 | 执行 | 执行只读阶段 |
| Actions 手动运行，`run_live_write=true` | 执行 | 执行 | 执行可写阶段 |
| Actions 手动运行，`run_live_journey=true` | 执行 | 执行 | 执行认证购买、课程学习、测验和正式考试报名完整旅程 |
| 多个选项为 `true` | 执行 | 执行 | 在同一个 Job 中按只读、可恢复写入、完整旅程的顺序执行 |
| 三个选项都为 `false` | 执行 | 执行 | 整个任务三跳过 |
| 定时任务 | 当前未配置 | 当前未配置 | 当前未配置 |

普通开发流程只需要：

```powershell
git push
```

Push 后，任务一和任务二会自动执行。任务三访问共享测试环境，为避免环境波动
或真实数据变更影响每次提交，目前只允许在 GitHub Actions 页面手动执行。
任务三默认执行只读阶段；可写阶段和完整业务旅程默认关闭，必须主动勾选。

## 4. 任务一：Candidate BFF regression

### 4.1 目标

检查 `candbff` 的编译质量、HTTP 接口合同、鉴权边界和 Handler 业务逻辑。

### 4.2 执行步骤

GitHub Actions 依次执行：

```powershell
go mod download
go vet ./...
go test ./...
go test -count=1 -coverprofile coverage.tmp ./handler ./server
```

当前覆盖率硬门槛为 `35%`。截至 `2026-08-06`，本地最近一次
Handler/Router 合并覆盖率为 `40.5%`。覆盖率会随代码变化，硬门槛以工作流
配置为准。

### 4.3 测试范围

- 健康检查和 JSON 404。
- 98 个 HTTP Method + Route 组合的精确合同。
- 78 个受保护路由的登录鉴权边界。
- CORS 允许和拒绝规则。
- 登录、回调、Cookie、Token 刷新和退出。
- 用户资料输入校验与格式标准化。
- 会员计划、会员记录、账单和取消规则。
- 商城、Pipeline、学习进度和课程报名。
- 资源包、文件归属、预览和查看地址。
- 测验答题、草稿、提交和完成。
- 考试历史、重考、回调和参数校验。
- 资格申请、证书和文件映射。
- 订单筛选、汇总、详情归属和取消状态。
- 发票归属、完成状态、Stripe URL 和 PDF。
- 消息列表、模板渲染、未读、已读和删除。
- 首页统计数据聚合。
- 公共配置不得泄露 Stripe Secret Key。
- Bundle 订单创建时的考生归属、支付模式、免考 JSON 和订单 ID 转发。
- 考试报名资料的规范化、路由实例 ID 优先级和来源系统标记。
- 课时完成写操作的考生归属、响应透传和微服务异常映射。

不会创建真实订单或修改真实账号。

### 4.6 不覆盖的内容

## 6. 任务三：Candidate live regression

### 6.1 目标

使用真实测试账号登录真实 Casdoor，并访问部署后的考生测试环境。任务三在
同一个 GitHub Actions Job 中包含默认只读阶段、可选可恢复写入阶段和可选完整
业务旅程阶段。完整旅程不会新增第四个 GitHub Actions Job。

### 6.2 驱动方式

任务三只在 GitHub Actions 手动运行时执行：

1. 打开仓库的 `Actions`。
2. 选择 `Candidate Portal Regression`。
3. 点击 `Run workflow`。
4. 选择要测试的分支。
5. 保持 `run_live_readonly` 为勾选状态。
6. 如需执行可恢复的真实写操作，额外勾选 `run_live_write`。
7. 如需执行认证购买、课程学习、测验和正式考试报名完整旅程，额外勾选 `run_live_journey`。
8. 点击绿色的 `Run workflow`。

手动运行时，任务一和任务二也会同时执行。
`run_live_readonly` 默认值为 `true`，`run_live_write` 和
`run_live_journey` 默认值均为 `false`。

#### 6.2.1 Run workflow 三个勾选项

GitHub Actions 的 `Run workflow` 面板中有三个可选项，它们都属于任务三，
但对应不同的测试范围和数据风险：

| GitHub 页面显示名称 | 工作流参数 | 做什么 | 是否修改测试环境数据 | 什么时候勾选 |
| --- | --- | --- | --- | --- |
| `Run the candidate test-environment read-only regression` | `run_live_readonly` | 使用真实考生账号登录 Casdoor，检查 `/health`、`/api/user/me` 和考生端 12 个主要页面，确认真实 BFF、微服务和页面读取链路正常 | 否，只读取真实数据 | 日常部署后巡检、上线前基础回归。默认勾选，通常保持勾选 |
| `Run controlled candidate test-environment writable regression` | `run_live_write` | 临时修改并恢复考生 `bio`；配置了 `E2E_LIVE_WRITE_BUNDLE_ID` 时，还会创建并取消一个未支付订单 | 是，但测试会在 `finally` 中自动恢复或取消 | 修改资料保存、订单创建、订单取消等写接口后使用。运行期间不要人工操作同一账号 |
| `Run paid certification, learning, quiz, and exam signup journey in the test environment` | `run_live_journey` | 复用同一个真实考生账号；优先继续已有待支付认证订单，否则购买新的可购买认证；认证已购买时复用已有认证。随后完成所有未完成课时、提交所有未完成测验，必要时依据考生页面公开的批改结果重试，最后提交正式考试报名或确认考试已经进入可预约、已预约、已有结果等后续状态 | 是，会留下已支付订单、认证归属、课时进度、测验结果和考试报名记录，不能自动清理 | 验证待支付恢复、认证购买、Stripe 回调、公共订单、Pipeline、学习、测验和考试报名完整链路时使用。运行前必须确认 Stripe Test Mode，并安排 Admin 清理 |

三个勾选项只控制任务三内部执行哪些阶段。无论如何选择，只要手动启动
`Candidate Portal Regression`，任务一和任务二仍会正常执行。

常用选择方式：

| 使用场景 | `read-only` | `writable` | `paid journey` | 说明 |
| --- | --- | --- | --- | --- |
| 普通真实环境巡检 | 勾选 | 不勾选 | 不勾选 | 推荐的日常选择，不修改业务数据 |
| 检查真实写接口 | 建议勾选 | 勾选 | 不勾选 | 先确认读取链路正常，再执行可自动恢复的写测试 |
| 检查购买、学习、测验和考试报名完整流程 | 建议勾选 | 按需 | 勾选 | 会产生支付、学习、测验和考试报名数据，运行前后需要 Admin 配合清理 |
| 只运行任务一、任务二 | 不勾选 | 不勾选 | 不勾选 | 任务三整个跳过 |

如果同时勾选多个选项，任务三按照以下顺序串行执行：

1. 只读回归。
2. 可恢复写入回归。
3. 认证购买、课程学习、测验和正式考试报名完整旅程。

- 会员 `/membership`
- 订单 `/orders`
- 消息 `/messages`
- 设置 `/settings`

每个页面会检查：

- 登录后没有跳回登录页。
- 页面标题正常显示。
- 页面发起的每类主体业务 API 在 45 秒内至少有一条完成；持续遥测、导航栏计数和同路径重复刷新不阻塞页面检查。

### 6.6 只读保护

真实只读测试允许：

- `GET`
- `HEAD`
- `OPTIONS`
- `POST /api/auth/refresh`
- `POST /api/telemetry`
- `POST /api/public/telemetry`

其他 `/api/**` 非只读请求会被浏览器测试直接阻止，并将测试判定为失败。

因此只读阶段不会：

- 创建或取消订单。
- 修改个人资料。
- 修改密码或邮箱。
- 标记或删除消息。
- 提交考试、测验或资格申请。
- 发起真实支付。

### 6.10 可写阶段

#### 6.10.1 目标

使用测试环境专用账号验证真实写接口，但只允许具备自动恢复或自动清理能力的
操作。任务三的可写阶段不会在 Push 或 Pull Request 时自动执行，避免并发
写入共享测试数据。

#### 6.10.2 驱动方式

任务三的可写阶段只在 GitHub Actions 手动运行并明确勾选时执行：

1. 打开仓库的 `Actions`。
2. 选择 `Candidate Portal Regression`。
3. 点击 `Run workflow`。
4. 选择要测试的分支。
5. 勾选 `run_live_write`。
6. 按需决定是否同时勾选 `run_live_readonly`。
7. 点击绿色的 `Run workflow`。

`run_live_write` 默认值为 `false`。工作流启动测试时还会注入
`E2E_LIVE_WRITE_ENABLED=true`，测试源码会同时检查该开关，防止本地或其他
Job 误执行。

启用可写阶段的任务三运行使用独立并发组且禁止 `cancel-in-progress`。普通
Push 不会中断正在执行的可写阶段；同一分支重复启动可写阶段时会排队串行
执行，避免清理逻辑因自动取消而来不及运行。

#### 6.10.3 Secrets 和 Variables

可写阶段复用任务三的三个必需 Repository Secrets：

- `E2E_CANDIDATE_BASE_URL`
- `E2E_CANDIDATE_USERNAME`
- `E2E_CANDIDATE_PASSWORD`

可选 Repository Variable：

- `E2E_LIVE_WRITE_BUNDLE_ID`

`E2E_LIVE_WRITE_BUNDLE_ID` 必须指向测试环境中允许当前测试考生购买、价格大于
零、创建后处于可取消状态的专用 Bundle。未配置时，订单创建取消测试会显示
为跳过，不影响资料更新恢复测试。

#### 6.10.4 执行步骤

任务三完成共用的依赖安装、类型检查和 Chromium 安装后执行：

```powershell
npm run test:e2e:live:write
```

#### 6.10.5 当前测试范围

当前包含 1 条必跑写测试和 1 条可选写测试：

- 必跑：读取当前考生资料，临时修改 `bio` 为唯一标记，确认真实读取结果已更新，
  然后在 `finally` 中恢复原值并再次确认。
- 可选：创建专用 Bundle 的未支付订单，确认获得真实订单 ID，并在 `finally`
  中调用 `/api/orders/cancel` 清理该订单。

订单测试明确拒绝 `COMPLETED`、`PAID` 或 `SUCCESS` 状态。专用商品如果会创建
免费或已完成订单，不得配置到该 Variable。

#### 6.10.6 清理和失败恢复

- 资料测试无论断言成功还是失败都会尝试恢复原始 `bio`。
- 订单测试只要取得 `bundle_order_ulid`，无论后续断言成功还是失败都会尝试
  取消订单。
- 如果清理接口本身失败，Job 必须保持失败，不能把残留数据伪装成成功。
- 工作流不会因为同分支的新 Push 自动取消正在运行的可写回归。
- 测试不执行密码、邮箱、真实支付、考试报名、资格申请或学习进度写入。
- 执行任务三的可写阶段前，应避免同一测试账号被人工同时操作。

#### 6.10.7 测试目录和报告

- `candweb/vue-web/e2e-live/write.spec.ts`
- `candweb/vue-web/e2e-live/auth.setup.ts`
- `candweb/vue-web/e2e-live/support/live.ts`
- `candweb/vue-web/playwright.live.config.ts`

失败时上传 `candidate-live-regression-report`，只包含关闭 Trace、截图和视频后的
Playwright HTML 报告，保留 3 天。

### 6.11 完整业务旅程阶段

#### 6.11.1 测试范围

`run_live_journey=true` 时，在任务三内部额外执行一条连续的真实环境旅程，
其中包含购买、学习、测验和正式考试报名四个阶段：

- 认证购买：逐个读取商城认证详情，自动选择当前账号可购买、支付金额大于 0
  且包含课程的认证；取消默认课程豁免，检查考生资料完整，创建订单，打开
  Stripe Embedded Checkout，使用 Stripe Test Mode 测试卡支付，并验证进入
  支付成功页。
- 课程学习：等待 Pipeline 创建完成，从我的认证进入该认证和当前课程，逐个完成
  所有不受测验阻塞的未完成课时；测验完成后再次处理原先被课时测验阻塞的课时，
  最终要求全部课时处于已完成状态。
- 课程测验：要求认证至少配置一个测验，逐个提交所有未完成测验。首次提交未通过
  时，只使用考生页面公开展示的详细批改结果重新答题，最终要求所有测验均通过，
  不再把“没有可用测验”静默当作成功。
- 正式考试：等待 Pipeline 从学习状态推进到考试状态。如果是待报名状态，通过
  考生页面提交正式考试报名资料并确认考试记录已经创建；如果此前已经报名，则
  确认当前状态已经是可预约、已预约、可查看结果、重考或认证后续状态。

任务不会自动操作第三方考试供应商页面完成正式考试答题，也不会伪造正式考试
成绩。第三方考试实际答题、预约时段选择、改期、取消和成绩回调仍需供应商测试
环境或人工配合。

#### 6.11.2 Stripe 配置

GitHub Actions 不需要保存 Stripe Dashboard 账号、密码、Secret Key 或测试卡号。
必须由测试环境的支付服务提前配置 Stripe Test Mode Key。浏览器测试使用 Stripe
公开测试卡 `4242 4242 4242 4242`、任意未来日期和任意 CVC；这些不是 Secret。

如果测试环境误用了 Stripe Live Mode，禁止运行完整旅程。

#### 6.11.3 账号和可选 Variable

完整旅程复用任务三原有的三个 Secrets：

- `E2E_CANDIDATE_BASE_URL`
- `E2E_CANDIDATE_USERNAME`
- `E2E_CANDIDATE_PASSWORD`

完整旅程会操作部署后的真实 `candweb` 页面，不会使用当前 GitHub Actions
工作区临时启动一个前端。测试依赖当前版本加入的课程、测验和考试报名稳定
`data-testid` 页面标记，因此第一次启用完整旅程，或者修改商城、结账、我的
认证、课程学习、测验和考试报名页面后，必须先将对应分支的 `candweb` 部署到
`E2E_CANDIDATE_BASE_URL`，再运行任务三。只执行 `git push` 会更新测试脚本，
不会自动更新该地址上的前端服务。

不需要增加另一个考生账号，也不需要配置 Bundle、Pipeline、Course、Lesson 或
Quiz ID。测试会逐个检查商城认证详情、公共订单列表和当前账号已有的 Candidate
Pipeline，并按照以下顺序选择完整旅程：

1. 如果存在对应商品、仍可继续支付的 `BUNDLE_PURCHASE` 公共订单，进入 `/orders`
   点击该商品行的“继续支付”，恢复原订单，不再创建重复订单。
2. 如果没有可恢复订单，选择第一个 `can_purchase=true`、支付金额大于 0、关联
   Pipeline 且包含课程的认证，创建新订单并支付。
3. 如果当前没有可购买认证，但账号已经拥有一个付费且包含课程的认证，复用已有
   Candidate Pipeline，跳过支付，继续验证认证详情、全部课时、全部测验和正式
   考试报名或后续状态。

候选认证只从 `/certifications` 页面当前实际渲染的商城卡片中选择，避免接口
后续分页中的商品无法通过页面点击进入。恢复待支付订单时，测试会同时校验公共
订单的 `biz_ref_ulid`、商品名称、业务类型、订单状态和支付状态，避免把其他
商品的阻塞订单误认为当前认证订单。
支付金额使用商城商品的 `display_amount_min`、`display_amount_max` 判断；购买前
不会要求 `payment_preview`，因为付款预览需要在订单创建后才会生成。
结账资料页仅在页面实际提供认证协议复选框时勾选；认证与会员组合商品不显示
该协议属于正常流程，测试会直接继续下一步。
Stripe 表单会等待动态出现的邮编字段并填写测试地址，避免表单因 ZIP 为空停留在
`Processing`。提交后首先等待对应公共订单进入已支付或已完成状态，再确认
Candidate Pipeline 已创建或仍然存在。对于认证与会员组合商品，付款前可能已经
存在 Candidate Pipeline，因此不能只根据 Pipeline 存在判断付款成功。

成功页跳转只作为新购支付返回体验信号，不再阻塞后续学习验证；从订单列表继续
支付时，页面按产品设计保留在 `/orders` 并刷新订单。完整旅程包含真实写入，因此
`live-journey` 禁止自动重试。恢复历史待支付订单失败时不会擅自取消原订单；只有
本轮新创建且尚未支付的订单在测试失败时才会尝试自动取消。已支付订单仍不会自动
取消。

可选 Repository Variable：

- `E2E_STRIPE_TEST_EMAIL`

如果不配置，测试使用固定的非真实测试邮箱。

#### 6.11.4 数据清理

完整旅程会产生已支付测试订单、认证归属、课件进度、测验结果和考试报名记录。
考生不能取消已支付订单，当前也没有经过确认的自动回滚合同，因此测试不会猜测
调用 Admin 取消接口或篡改业务字段。

需要重新制造“新购买”场景或清理测试数据时，由 Admin 或测试数据维护人员：

1. 清理或取消上次已支付测试订单。
2. 恢复该考生至少一个认证的 `can_purchase=true` 状态。
3. 重置刚购买认证的课件进度和测验结果。
4. 清理或重置该认证对应的考试报名记录。
5. 确认测试环境仍使用 Stripe Test Mode。

如果只是重复验证任务本身，测试可复用账号已有认证继续执行。已经完成的课时和
测验会校验完成状态，已经报名的考试会校验后续状态，不会重复写入；但这种重复
运行不会再次覆盖“创建新订单”“实际完成新课时”“首次提交新测验”或“首次考试
报名”分支。要重新覆盖这些写入分支，必须由 Admin 重置对应测试数据；要覆盖待
支付恢复分支，必须保留一个真实可继续支付的测试订单。

完整旅程启用独立串行并发保护，不会被同分支的新 Push 自动取消。

## 7. 任务和代码改动的对应关系

| 改动类型 | 必须检查或修改的任务 |
| --- | --- |
| 新增、删除、重命名 BFF 路由 | 任务一，更新 `candidateRouteContract` |
| 修改 Handler 参数或响应 | 任务一，增加成功、失败、归属和状态测试 |
| 修复后端业务 Bug | 任务一，增加能复现旧 Bug 的回归测试 |
| 修改登录、Token、订单按钮或支付返回体验 | 任务二 |
| 新增考生主页面 | 任务二和任务三 |
| 修改页面依赖的真实只读接口 | 任务一和任务三 |
| 修改 Casdoor 登录或 Callback | 任务一、任务二和任务三 |
| 修改用户资料写接口 | 任务一、任务二和任务三的可写阶段 |
| 修改 Bundle 创建或订单取消接口 | 任务一、任务二和任务三的可写阶段 |
| 修改认证购买、Stripe 支付或课程学习流程 | 任务二和任务三的完整业务旅程阶段 |
| 新增真实数据写操作回归 | 不得加入任务三的只读阶段；仅可加入任务三的可写阶段并提供恢复或清理机制 |
| 修改 GitHub Actions 驱动条件 | 更新 Workflow 和本文档的驱动矩阵 |

## 8. 新增任务时的维护规则

新增第四个或后续任务时，必须完成：

1. 明确任务名称和唯一 Job ID。
2. 明确是 Push、Pull Request、手动还是定时驱动。
3. 明确是否访问真实环境。
4. 明确是否会创建或修改业务数据。
5. 明确测试账号和最小权限。
6. 明确测试数据创建与清理方案。
7. 明确失败报告保存哪些文件、保留多少天。
8. 明确哪些 Secrets 或 Variables 是必需的。
9. 将测试代码放入统一目录，不散落到生产代码目录。
10. 更新本文档的任务总览、驱动矩阵、测试范围和变更记录。

如果任务会产生真实订单、支付、考试报名或资格申请，必须使用
`workflow_dispatch` 手动触发，除非已经具备可靠的自动清理机制。

## 9. 修改任务时的维护规则

修改现有任务时，必须同步检查：

- Workflow 中的 Job 名称、`if` 条件和超时时间。
- `package.json` 或 Go 命令。
- Playwright Config、测试目录和报告目录。
- 测试数量和页面清单。
- GitHub Secrets 名称。
- 覆盖率门槛。
- 文档里的驱动矩阵和测试范围。

修改后至少运行对应的本地检查。

任务一相关修改：

```powershell
cd candbff
go vet ./...
go test -count=1 ./...
```

任务二相关修改：

```powershell
cd candweb/vue-web
npm run build
npm run test:e2e:typecheck
npm run test:e2e
```

任务三相关修改：

```powershell
cd candweb/vue-web
npm run test:e2e:typecheck
npm run test:e2e:live -- --list
npm run test:e2e:live:write -- --list
npm run test:e2e:live:journey -- --list
```

只有在本地安全配置了环境变量，并确认目标是测试环境时，才运行完整的
`npm run test:e2e:live`。只有在明确允许修改测试数据、配置了测试账号，并
确认恢复或清理机制有效时，才运行完整的 `npm run test:e2e:live:write`。只有在
确认 Stripe Test Mode、账号至少有一个可购买或已拥有且包含课程和测验的认证、
考生资料满足考试报名要求，并且 Admin 清理安排已就绪时，才运行
`npm run test:e2e:live:journey`。

## 10. 删除任务时的维护规则

删除任务时不得只删除 GitHub Actions Job，还必须检查：

1. 删除对应 Workflow Job。
2. 删除不再使用的测试目录和配置文件。
3. 删除不再使用的 `package.json` Script。
4. 删除不再使用的报告目录配置。
5. 确认相关 Secrets 是否可以从 GitHub 删除。
6. 更新本文档的任务总览和驱动矩阵。
7. 更新其他引用该任务的 README 和 Pull Request 模板。
8. 确认删除后仍有其他测试层保护原来的关键风险。
