# 考生端优化与缺陷清单

整理日期：2026-10-21。来源为客户《GFI Portal Feedback》（截至 10 月 9 日，共 15 页），并结合当前仓库作初步评估。以下编号用于后续逐项讨论；复选框表示本次代码修改状态，已勾选仍需部署到测试服验收。

复杂度口径：**低**为局部文案或界面调整；**中**需要联动现有接口、数据或多个页面；**高**涉及认证、支付、学习规则、数据迁移或跨微服务改造。实际工期仍需在复现问题、确认接口契约和业务规则后评估。

## 注册与登录（第 2–3 页）

- [ ] **C-01｜密码规则｜中**：注册密码至少 8 位，同时包含字母和数字。注册入口在 Casdoor；按本次沟通，此项不修改 `candbff`/`candweb`，留待 Casdoor 处理。
- [ ] **C-02｜即时验证邮箱验证码｜中到高**：邮箱旁增加“验证验证码”操作，输入后立即反馈结果，不让用户填完其他字段才发现验证码错误。需要核对 Casdoor 注册流程和验证码接口是否支持分步校验。
- [ ] **C-03｜注册账号已存在的提示｜中**：客户指出现有英文提示 `Email already exists`；建议替换为原文 `Unable to complete registration. Please sign in or use a different email.` 手机注册同样使用不暴露账号状态的通用提示。由 Casdoor 修改，用户自行搜索替换；服务端响应也应避免暴露账号存在性。
- [ ] **C-04｜手机号所有权验证｜高；待客户提供短信服务**：允许手机登录前，在个人资料中完成“输入手机号 → 发送 OTP → 验证 → 标记为已验证”，登录只认可已验证号码。需客户提供短信供应商/API 文档、可用的测试和正式环境凭证、短信签名与验证码模板及审批状态、发送国家/地区和号码格式、频率/费用限制；还需确认 Casdoor 的手机号验证字段与手机号登录配置。取得资料后再做联调。
- [ ] **C-05｜不存在用户的登录提示｜实现低**：客户要求替换为原文 `The user does not exist. Please sign up first.` 由 Casdoor 修改，用户自行搜索替换。该文案会暴露账号是否存在，与 C-03 的安全诉求相反；上线前应让客户确认此取舍。

## 个人资料与账号安全（第 4 页）

- [ ] **C-06｜安全地修改邮箱｜高；代码已改用 Casdoor 验证码，待联调**：安全设置分别向旧邮箱和新邮箱发送 Casdoor 验证码；同一次提交先校验旧邮箱验证码，再由 Casdoor 校验新邮箱验证码并修改账号邮箱。BFF 不再使用 Redis，也不再生成确认链接。部署需确认 Casdoor 考生应用配置了适用于 `reset` 的邮件供应商、组织的 Email 字段允许用户修改；当前请求使用 `captchaType=none`，若 Casdoor 启用 CAPTCHA，需补充相应验证码组件和参数。Casdoor 会按应用配置限制验证码发送频率，连续向两个邮箱发送时可能需等待。完成时会清除当前浏览器的 BFF 登录 cookie；其他设备和 Casdoor SSO 会话失效尚未实现，因此暂不勾选完成。
- [x] **C-07｜调整资料信息架构｜低；代码已完成**：邮箱和修改密码放在“账号安全”，普通资料页不再显示 Login ID；移除 Display Name、Real Name 的编辑项。已有姓名数据仍保留在 Casdoor，保存普通资料时不覆盖这些字段。
- [x] **C-08｜个人头像｜中；代码已完成**：资料页可选择 JPEG/PNG、调整方形裁剪并预览，BFF 限制格式/大小后上传 Casdoor 资源，保存 `Avatar` 字段。头像已可从个人资料接口读取；营销页面如需展示仍需指定位置并联调。
- [x] **C-09｜语言偏好｜中；代码已完成**：中文/英文切换写入 Casdoor `Language` 字段，登录后读取并恢复账号偏好；需在测试服验证 Casdoor 字段更新权限。
- [ ] **C-10｜个人链接｜中**：增加 Website、LinkedIn、X 链接，包含格式校验和展示位置。
- [ ] **C-11｜营销通知偏好｜高**：分别允许订阅或退出“产品发布与公告”“优惠与促销”，并让发送端实际遵守偏好；需要同意记录及审计。
- [ ] **C-12｜账号关闭申请｜高**：在应用内提交删除申请，14 天内可撤回；到期执行删除/匿名化并记录审计。需先确定订单、证书等依法或业务上必须保留的数据。

## 报名、支付与豁免申请（第 9–10 页）

- [ ] **C-21｜报名资料单一来源｜中**：报名页从个人资料预填，原则上只读，并提供“Edit in Profile”入口；需检查未完善资料时如何返回报名流程。
- [ ] **C-22｜出生日期校验｜中**：资料页不允许未来日期，并按最低年龄限制校验。最低年龄数值需要客户确认，前后端均应执行相同规则。
- [ ] **C-23｜条款及隐私政策链接｜低；等待素材**：报名勾选区域链接至正式 CFtP Terms of Service 和 Privacy Policy；客户表示文档后续提供。
- [ ] **C-24｜优惠码导致支付字段消失｜中；先复现**：客户报告输入优惠码后付款字段消失。需按其录屏复现，核对优惠码预览、错误/加载状态及支付组件显示条件，修复后覆盖有效、无效及移除优惠码场景。
- [ ] **C-25｜豁免模板预览/下载报错｜中**：排查附件配置指向的文件是否存在、对象存储键及预览/下载地址；同时明确后台何处上传 Verification Form 模板。
- [ ] **C-26｜申请附件历史｜中到高**：用户可查看历次提交的文件，不仅看到当前申请/最新附件；需确认上游是否保留版本和访问授权。
- [ ] **C-27｜管理员操作时间格式｜低到中**：修复申请详情中 Admin Action At 为 null/unset 时的异常显示，并明确真正缺失时间时的文案；若上游未记录时间则需服务侧修复。

## 旧证书验证（第 12 页）

- [ ] **C-31｜旧证书可验证｜高**：客户称旧证书在现有验签页全部失败，并认为旧证书数据迁移属于交付范围。需核实历史证书清单、旧签名密钥/记录和撤销状态，再在迁移旧信任链、重签或可信旧证书核验通道中确定方案；不得把“无新式 PDF 签名”直接判为伪造。
- [ ] **C-32｜简化验证结果｜低到中**：默认展示清晰的“有效/无效”结果与持有人等关键信息，区分“数字签名验证”和“历史记录核验”；七步技术检查折叠到“查看技术详情”，减少 PKI 术语。

## 会员、订单与通知（第 13–15 页）

- [ ] **C-33｜会员页结构及文案｜低到中**：Billing 移至 Purchase History；Current Membership 改为 Your Plan；未入会时给出加入 Affiliate/比较方案入口；方案卡移除 Tier Level，提供 Join Now 和 [Learn more](https://globalfintechinstitute.org/membership/benefits/) 链接。

- [ ] **C-37｜订单名称与状态｜低到中**：Orders 改为 Purchase History；解释或重命名“Wait Payment”，并区分待支付、支付处理中和支付失败，先核对实际订单状态语义。

- [ ] **C-39｜通知时间呈现｜低到中**：7 天内显示“2 小时前/1 天前”，超过 7 天显示绝对时间；审计日志始终显示绝对时间。还需核对服务端时间是否以 UTC 存储，不能仅靠前端格式化掩盖存储问题。
